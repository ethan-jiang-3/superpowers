# 02 — 多平台适配

## 这个问题为什么重要

Superpowers 声称支持 Claude Code、Cursor、Codex、Gemini CLI、OpenCode、Copilot CLI 六个平台。但每个平台的 skill 系统、hook 机制、工具命名都不一样。怎么做到"写一份 SKILL.md，六个平台都能跑"？

答案是**三层适配**：bootstrap 注入层、skill 发现层、工具名翻译层。每一层用不同的策略处理平台差异。

---

## 三层适配架构

| 层 | 问题 | 策略 |
|---|------|------|
| **Bootstrap 注入** | using-superpowers 怎么进到 agent 上下文？ | 4 种路径：hook JSON 注入、文件引用、JS 消息转换、description 自动触发 |
| **Skill 发现** | 平台怎么找到和加载 skill 文件？ | 3 种路径：原生 skill 系统、显式路径声明、JS config hook |
| **工具名翻译** | skill 里写的 `TodoWrite`、`Task` 在别的平台叫什么？ | 4 份工具映射表 + 1 份行内注入 |

---

## 六个平台逐一分析

### 1. Claude Code（标准平台）

**清单：** `.claude-plugin/plugin.json`
**Bootstrap：** `hooks/hooks.json` → `session-start` 脚本 → JSON `hookSpecificOutput.additionalContext` 注入
**Skill 工具名：** `Skill`（大写 S）
**工具名：** 不翻译——Claude Code 是标准平台。所有 skill 文件用 Claude Code 原生工具名（`TodoWrite`、`Task`、`Read`、`Write`、`Edit`、`Bash`）
**检测方式：** `CLAUDE_PLUGIN_ROOT` 已设置且 `COPILOT_CLI` 未设置

**特殊问题：**
- `session-start` 脚本 41 行的注释："Claude Code reads BOTH additional_context and hookSpecificOutput without deduplication, so we must emit only the field the current platform consumes." 如果两个字段都输出，内容注入两次。

---

### 2. Cursor

**清单：** `.cursor-plugin/plugin.json`——显式声明 `"skills": "./skills/"`、`"agents": "./agents/"`、`"commands": "./commands/"`、`"hooks": "./hooks/hooks-cursor.json"`（比 Claude Code 更显式）
**Bootstrap：** `hooks-cursor.json` → 同 `session-start` 脚本 → JSON `additional_context`（snake_case，顶层字段）
**Skill 工具名：** `Skill`——与 Claude Code 兼容
**工具名：** 不翻译——Cursor 兼容 Claude Code 工具名
**检测方式：** `CURSOR_PLUGIN_ROOT` 已设置。注意代码注释："Cursor sets CURSOR_PLUGIN_ROOT (may also set CLAUDE_PLUGIN_ROOT)"——所以 Cursor 检测必须优先于 Claude Code

**差异：**
- Hook 配置文件独立（`hooks-cursor.json`，不是默认的 `hooks.json`）
- Hook 格式不同：camelCase `sessionStart`，有 `"version": 1`，没有 matcher
- JSON 输出格式不同：snake_case `additional_context` vs PascalCase 嵌套

---

### 3. Codex CLI / Codex App

**清单：** `.codex-plugin/plugin.json`——最丰富的清单文件，含 marketplace 元数据（`displayName`、`shortDescription`、`longDescription`、`category`、`capabilities`、`defaultPrompt`、`composerIcon`、`logo`、`brandColor`，甚至 `website`、`privacyPolicyUrl`、`termsOfServiceUrl`）。没有 hooks 配置。

**Bootstrap：** **没有。** 不执行脚本，不注入文件。Codex 自动发现 `skills/` 目录下的 skill，读 description frontmatter。`using-superpowers` 的 description `Use when starting any conversation` 让 Codex 在 session 启动时自动加载。

**Skill 工具名：** 不需要显式调用——skills 自动加载。`codex-tools.md` 写的是 "Skills load natively -- just follow the instructions."

**工具名翻译（`codex-tools.md`）：**

| Skill 中的名称 | Codex 等价物 |
|-------------|------------|
| `Task` | `spawn_agent` / `wait_agent` / `close_agent` |
| `TodoWrite` | `update_plan` |
| `Skill` | N/A（自动加载） |

**特殊限制：**
- Subagent 需要 `multi_agent = true` 在 `~/.codex/config.toml` 的 `[features]` 下
- Codex App sandbox 模式下：agent 不能 push 或创建 PR。detached HEAD 是常态。agent 提交所有改动后告诉用户用 App 的 "Create branch" 或 "Hand off to local"
- 环境检测建议写在 `codex-tools.md` 里：用 `GIT_DIR != GIT_COMMON_DIR` 检测 worktree/sandbox 状态

---

### 4. Gemini CLI

**清单：** `gemini-extension.json`——`"contextFileName": "GEMINI.md"`
**Bootstrap：** `GEMINI.md` 文件引用——`@./skills/using-superpowers/SKILL.md` + `@./skills/using-superpowers/references/gemini-tools.md`。**这是唯一默认加载工具映射的平台。**
**Skill 工具名：** `activate_skill`。Gemini 在 session 启动时加载 skill 元数据，按需激活完整内容。

**工具名翻译（`gemini-tools.md`）：**

| Skill 中的名称 | Gemini CLI 等价物 |
|-------------|-----------------|
| `Read` | `read_file` |
| `Write` | `write_file` |
| `Edit` | `replace` |
| `Bash` | `run_shell_command` |
| `TodoWrite` | `write_todos` |
| `Skill` | `activate_skill` |
| `Task`（subagent） | `@agent-name` 语法（如 `@generalist`） |
| `WebSearch` | `google_web_search` |

**特殊能力：**
- Gemini CLI 有 Claude Code 没有的工具：`list_directory`、`save_memory`、`ask_user`、`tracker_create_task`、`enter_plan_mode`/`exit_plan_mode`
- Subagent 用 `@generalist` + 填充后的 prompt template。多个 `@generalist` 调用并行执行

---

### 5. OpenCode

**清单：** `.opencode/plugins/superpowers.js`——JS 插件，不是 JSON 清单
**Bootstrap：** 两个 JS hook——
1. `config` hook：把 skills 路径注入 OpenCode 的 live config（`config.skills.paths.push(superpowersSkillsDir)`），不需要 symlink
2. `experimental.chat.messages.transform` hook：在每个 agent step 时检查第一条用户消息是否需要 bootstrap 注入。读取 `SKILL.md`，去 frontmatter，组装 OpenCode 专用工具映射，插入到第一条用户消息开头

**Skill 工具名：** OpenCode 原生 `skill` 工具
**工具名翻译：** **行内注入**——不依赖单独的 references 文件。bootstrap 方法把工具映射直接写在注入的消息里：

| Skill 中的名称 | OpenCode 等价物 |
|-------------|--------------|
| `TodoWrite` | `todowrite` |
| `Task`（subagent） | `@mention` |
| `Skill` | OpenCode 原生 `skill` 工具 |

**特殊问题：**
- `messages.transform` 在每个 agent step（不只是每个 turn）都触发——因为 OpenCode 每次从 DB 重新加载消息。做了模块级缓存和双重注入保护
- Windows 有已知问题：git+https URL 的 cache 路径、Bun 找不到 `git.exe`。workaround：通过 npm 安装
- 旧 symlink 安装方式需要迁移
- Skill 优先级：项目 skills > 个人 skills > Superpowers skills

---

### 6. Copilot CLI

**清单：** 使用同 Claude Code 的 marketplace（`obra/superpowers-marketplace`）
**Bootstrap：** 同 `hooks/hooks.json` + `session-start` 脚本。检测到 `COPILOT_CLI=1` 环境变量时输出 SDK 标准 JSON 格式（`additionalContext` 顶层字段）
**Skill 工具名：** `skill`（小写）。`skills/using-superpowers/SKILL.md` 里写 "In Copilot CLI: Use the `skill` tool."
**检测方式：** `CLAUDE_PLUGIN_ROOT` 已设置 **且** `COPILOT_CLI=1`

**工具名翻译（`copilot-tools.md`）：**

| Skill 中的名称 | Copilot CLI 等价物 |
|-------------|-----------------|
| `Read` | `view` |
| `Write` | `create` |
| `Edit` | `edit` |
| `Bash` | `bash` |
| `Skill` | `skill` |
| `Task`（subagent） | `task` + `agent_type: "general-purpose"` |
| `TodoWrite` | `sql`（操作内置 `todos` 表） |
| `WebSearch` | 不存在——用 `web_fetch` + 搜索 URL |

**Copilot CLI 独有的工具（skill 不用的，但值得一提）：**
- `bash` 支持 `async: true`——持久异步 shell session（Claude Code 没有等价物）
- `store_memory`——跨 session 持久化
- `report_intent`——更新 UI 状态栏
- `sql`——查询 session 的 SQLite 数据库
- 原生 GitHub MCP 工具（`github-mcp-server-*`）

---

## 适配策略总结

| 平台 | Bootstrap 路径 | Skill 发现 | Skill 工具名 | 工具翻译 | 复杂度 |
|------|--------------|----------|------------|--------|--------|
| **Claude Code** | Hook JSON 注入 | 原生自动发现 | `Skill` | 无（标准） | 低 |
| **Cursor** | Hook JSON 注入（camelCase） | 显式路径声明 | `Skill` | 无（兼容） | 低 |
| **Codex** | 无（description 触发） | 自动发现 | N/A（自动加载） | `codex-tools.md` | 中 |
| **Gemini CLI** | `@` 文件引用 | 原生扩展系统 | `activate_skill` | `gemini-tools.md`（默认注入） | 中 |
| **OpenCode** | JS 消息转换 | JS config hook | `skill`（小写） | 行内注入 | 高 |
| **Copilot CLI** | Hook JSON 注入（SDK 格式） | 同 CC marketplace | `skill`（小写） | `copilot-tools.md` | 中 |

---

## 三个值得注意的设计决策

### 1. 工具翻译不是自动的

Skill 文件里写的是 Claude Code 工具名。非 Claude Code 平台上的 agent 需要**主动读对应平台的 `*-tools.md` 文件**来做翻译。唯一例外是 Gemini CLI——`GEMINI.md` 默认用 `@` 引用把 `gemini-tools.md` 注入上下文。

这个设计假设：agent 在需要时会自己去读工具映射。对于 Claude Code 和 Cursor（不需要翻译），这个假设成立。对于其他平台，取决于 agent 是否真的会去读——这也是为什么 Gemini CLI 和 OpenCode 选择了"主动注入"而不是"等 agent 去读"。

### 2. `session-start` 的平台分发是运行时检测，不是编译时配置

三个环境变量（`CURSOR_PLUGIN_ROOT`、`CLAUDE_PLUGIN_ROOT`、`COPILOT_CLI`）+ 优先级顺序（Cursor 优先于 Claude Code 优先于 Copilot/SDK），一份脚本适应六个平台。不需要编译，不需要用户选择平台。

代价是：评论区解释了平台 bug（Claude Code 不 deduplicate 两个 JSON 字段），说明了这是一个试错积累出来的方案，不是设计出的。

### 3. Codex 和 Gemini 的 manifest 比 Claude Code 丰富得多

Codex 的 `plugin.json` 有 `interface` 对象（displayName、logo、brandColor、screenshots、defaultPrompt）。Gemini 的 `gemini-extension.json` 有 `contextFileName` 概念。Claude Code 的 `plugin.json` 相比之下极简——只有 name、version、author、keywords。

这说明不同的平台对"插件"的想象不同：Codex 认为插件是 marketplace 产品（需要展示元数据），Claude Code 认为插件是代码包（不需要展示层）。
