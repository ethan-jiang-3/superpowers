# Superpowers 高级 — 扩展方法论本身

## 高级解决什么问题

初级解决了"**能不能做出来**"——从想法到交付的完整管线。
中级解决了"**能不能更快更好地做出来**"——工作区隔离、subagent 并行、系统化调试、代码 review。

高级解决的是一个完全不同的问题："**能不能扩展这套方法论本身？**"

当你用 Superpowers 做了足够多的项目后，你会遇到两种情况：
1. **你有多个独立的问题需要同时解决**，但中级的 SDD 是顺序执行的
2. **你想创造新的技能**来覆盖 Superpowers 没覆盖的场景

高级就是为这两种情况准备的。

---

## 高级的独特定位

高级和初中级有本质区别：

- **初级和中级是操作方法**：它们教你**使用** Superpowers 的各种技能来完成软件开发
- **高级是元方法**：它教你**创造** Superpowers 的新能力，扩展这套方法论的边界

高级只有 2 个技能，但它们的性质完全不同：

| 属性 | 初级 | 中级 | 高级 |
|------|------|------|------|
| 做什么 | 完成一个项目 | 更快更好地完成项目 | 扩展方法论本身 |
| 技能数 | 7 | 5 | 2 |
| 性质 | 操作方法 | 增强方法 | **元方法** |
| 用户类型 | 任何用 AI 写代码的人 | 需要高效高质量交付的人 | 想创造新技能/解决 Superpowers 不覆盖的问题 |
| 使用频率 | 每个项目都用 | 大部分项目用 | 偶尔用，但每次用的影响深远 |

## 高级技能的选入逻辑

### 为什么是这 2 个

高级的 2 个技能解决了两个"元问题"：

**元问题 1：并行性**

中级的 SDD 是顺序执行的——一个 task 接一个 task。当你有多个**完全独立**的问题时（比如 3 个不同文件的测试失败，根因各不相同），顺序执行浪费时间。

`dispatching-parallel-agents` 解决：把独立问题分派给并行 agent，同时解决，然后整合。3 个问题同时解决 = 时间效率 3x。

**元问题 2：技能创造**

Superpowers 覆盖了常见场景，但你的项目可能遇到它没覆盖的问题。比如你发现 agent 在某个特定类型的任务上总是犯错——你需要一个新技能来防止这个错误。

`writing-skills` 解决：用 TDD 的方法论创造新技能。RED（无技能 baseline，观察 agent 怎么犯错）→ GREEN（写最小技能，验证 agent 现在做对了）→ REFACTOR（堵上 agent 找到的新借口）。写技能的过程和写代码的过程用的是同一套 TDD 纪律。

### 为什么高级只有 2 个

因为元方法本身就应该少。大多数用户永远不需要创造新技能——他们用初级和中级的技能就能完成所有工作。高级不是为了"进阶"，而是为了"扩展"。

## 高级管线的设计哲学

### 元 TDD：方法论上的 TDD

高级的核心哲学：**TDD 不只适用于代码，也适用于方法论。**

`writing-skills` 把这个哲学体现得最彻底：
- **测试用例** = 压力场景（用 subagent 模拟 agent 在特定场景下的行为）
- **生产代码** = 技能文档（SKILL.md）
- **RED** = Agent 在没有技能的情况下违反规则（baseline 行为）
- **GREEN** = Agent 在有技能的情况下遵守规则
- **REFACTOR** = 堵上 agent 找到的新漏洞和借口

这和初级的 TDD 技能是同构的——只是测试的对象从"代码"变成了"agent 的行为"。如果你理解了初级的 TDD，理解高级的 writing-skills 就只需要一个思维转换：把"测试验证代码行为"映射到"压力场景验证 agent 行为"。

### 并行哲学：独立问题不应排队

`dispatching-parallel-agents` 的哲学：**如果一个问题和另一个问题完全独立，它们不应该排队。**

这不是"快一点"的优化——它是结构性的效率提升。3 个 agent 同时调查 3 个不同的问题，它们互不干扰，同时完成。时间效率 3x，但更重要的是：每个 agent 的上下文只包含自己的问题域，不会被其他问题干扰。

但这个哲学有一个严格的前提：**问题必须真的独立。** 如果问题 A 的修复可能影响问题 B 的修复，并行 = 冲突。判断独立性是使用这个技能的核心能力。

## 学习建议

### 前提条件

进入高级之前：
- 中级的所有技能都熟练掌握（尤其是 SDD——因为并行调度依赖你对 subagent 行为的理解）
- 至少拥有 10+ 个用 SDD 完成的项目经验
- 遇到过至少一次"这些问题是独立的，我应该并行解决"的场景
- 对 Superpowers 的技能设计哲学有深入理解（特别是"借口 vs 真相"表格和 Red Flags 的设计原理）

### 学习顺序

**第一步：dispatching-parallel-agents（00）**

等一个真实的并行场景再学——不要为了学而创造场景。当你面对 3+ 个独立的测试失败或 bug，且你确认它们互不干扰时，用这个技能分派并行 agent。

关键体验：
- 独立性的判断——你怎么知道问题 A 和 B 是独立的？
- 每个 agent 的提示词怎么写才能让它聚焦且不越界？
- 结果整合——三个 agent 有没有改同一个文件？有没有冲突？

**第二步：writing-skills（01）**

这是 Superpowers 的"终极技能"。只有当你在实际工作中遇到"Superpowers 没有覆盖这个场景"的情况时，才需要学它。

创造第一个技能的关键：
- **先跑 baseline**：在没有技能的情况下，让 agent 面对压力场景，记录它是怎么失败的、用了什么借口
- **写最小技能**：针对这些具体的失败点写技能，不要加"以防万一"的内容
- **堵漏洞**：用更猛的压力测试找到 agent 的新借口，然后堵上

### 成功标志

- **并行自信**：你能准确判断哪些问题可以并行解决，哪些需要顺序处理
- **技能创造成功**：你创造了至少一个有效的新技能——跑过完整的 RED → GREEN → REFACTOR 周期，并且在实际项目中证明了它的效果
- **元认知**：你开始发现自己在想"这种情况需要一个技能来防止"——你开始用 Superpowers 的思维模式思考 Superpowers 本身

## 高级之后

Superpowers 的三个层级学完后，你已经掌握了：
- **怎么做一个项目**（初级：7 个技能，从想法到交付）
- **怎么高效高质量地做一个项目**（中级：5 个技能，隔离/并行/调试/review）
- **怎么扩展这套方法**（高级：2 个技能，并行调度/创造技能）

高级之后不是"学更多技能"——而是**用这套方法解决更多类型的问题**。你可能会：
- 为自己的特定技术栈创造专属技能（用 writing-skills）
- 并行处理大规模项目中的独立子系统（用 dispatching-parallel-agents + SDD）
- 回过头重新理解初级的哲学——你会发现初级里的"借口 vs 真相"表格和 Red Flags 设计，正是 writing-skills 在生产环境中的体现

这套方法论的最终目标不是让你"学会 14 个技能"——而是让你和你的 agent 形成一种**结构化、可验证、持续改进**的工作方式。技能文档只是这种工作方式的载体。
