# 02 — 证据先行（Verificationism）

## 这个问题为什么重要

Agent 说"完成了"。你相信它——直到运行测试发现 3 个失败。Agent 说"fix 好了"。你合并了——直到 prod 崩溃发现 fix 引入了新问题。

Agent 没有恶意。它在 LLM 的认知架构下，"我改了代码"的体感和"任务完成了"的体感是同一个东西。它不区分"做了"和"做对了"。

Superpowers 的 verification-before-completion 是专门针对这个问题的：**"looks done" 不是 "done"。**

---

## 核心原则

```
Claiming work is complete without verification is dishonesty, not efficiency.

Core principle: Evidence before claims, always.

Violating the letter of this rule is violating the spirit of this rule.
```

"效率"被重定义为"欺骗"。这不是修辞——是在重建 agent 的代价评估。如果"跳过验证"被定义为"欺骗"，agent 在合理化"只是效率而已"时需要先推翻这个定义。

---

## 5 步门函数

```
BEFORE claiming any status:

1. IDENTIFY: What command proves this claim?
2. RUN: Execute the FULL command (fresh, complete)
3. READ: Full output, check exit code, count failures
4. VERIFY: Does output confirm the claim?
   - If NO: State actual status with evidence
   - If YES: State claim WITH evidence
5. ONLY THEN: Make the claim

Skip any step = lying, not verifying
```

每步都是强制性的、有顺序的、不可跳过的。

### 步骤详解

**Step 1 — IDENTIFY**：在跑任何命令之前，"什么命令能证明这个 claim 是对的？" 阻止 agent 跑无关命令然后声称验证通过。

**Step 2 — RUN**：执行完整命令。"完整"和"新鲜"是关键词——上一次 run 的结果不算。"FULL"防止 agent 跑一半（"前 10 个 test 都过了所以..."）。

**Step 3 — READ**：检查完整输出。不能只看 exit code——0 exit code 可能有 5 个 skipped tests。

**Step 4 — VERIFY**：这里的布尔检查是关键。"Does output CONFIRM the claim?" 如果 output 不确认，不能说"应该没问题了"——必须说"不对，实际状态是...你看 output 这样说"。

**Step 5 — ONLY THEN**：门函数的核心机制。Agent 必须在通过前 4 步之后才能声称完成。声称放在门之后——不是在门之前。

---

## 语言学覆盖：防止话语绕道

最 subtle 的违规是：agent 不直接说"完成了"，而是用不同的措辞暗示完成而不触发规则。Verification skill 的回应是覆盖所有话语变体：

```
Rule applies to:
- Exact phrases ("Done", "Fixed", "Passing")
- Paraphrases and synonyms ("Ready", "All set", "Good to go")
- Implications of success
- ANY communication suggesting completion/correctness
```

这意味着 agent 不能说"Ready!"（这是 paraphrase），不能说"Looks good"（暗示完成），不能说"All tests passed"（声称成功）。只有经过门函数的、带证据的声明才是允许的。

Red Flags 列举了具体的语言信号：
- "should"（概率性语言替代证据）
- "probably"（同上）
- "seems to"（表象替代验证）
- "Great!"、"Perfect!"、"Done!"（验证前的满意表达）
- "我太累了，就这样吧"（疲惫作为借口）

## 具体 Claims 和它们实际需要的证据

| Claim | 需要的证据 | 不够的证据 |
|-------|---------|---------|
| Tests pass | Test 命令输出：0 failures | 上一次 run、should pass |
| Linter clean | Linter 输出：0 errors | 部分检查、推断 |
| Build succeeds | Build 命令：exit 0 | Linter 通过、log 看起来好 |
| Bug fixed | 原始症状的 test：通过 | 代码改了、assumed fixed |
| Regression test 通过 | 红-绿循环已验证 | Test 只通过一次 |
| Agent completed | VCS diff 显示改动 | Agent 自我报告 success |
| Requirements met | 逐行 checklist | Tests passing（不充分！） |

每一行都是具体的、可执行的标准。Agent 不能说"我没看到——标准是什么？"因为标准列在这里。

---

## 铁律的精确措辞

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE.

If you haven't RUN the verification command in THIS MESSAGE,
you cannot claim it passes.
```

"fresh" 是关键词。Agent 在 3 个 turn 前跑过 test，现在说"test are passing"——不行。必须是在当前消息中重新跑过。

---

## 和 TDD 的对称性

| TDD | Verification |
|-----|-------------|
| 没有先失败的 test 就没有生产代码 | 没有新鲜验证证据就没有完成声明 |
| "先看 test 失败"是强制步骤 | "先跑验证命令"是强制步骤 |
| RED → GREEN → REFACTOR | IDENTIFY → RUN → READ → VERIFY → ONLY THEN |

两者都是门函数模式，都要求在行动前产生外部证据。

## 借口反驳表

| 借口 | 现实 |
|------|------|
| "Should work now" | RUN the verification |
| "I'm confident" | Confidence ≠ evidence |
| "Just this once" | No exceptions |
| "Linter passed" | Linter ≠ compiler/tests |
| "Agent said success" | Verify independently |
| "I'm tired" | Exhaustion ≠ excuse |
| "Partial check is enough" | Partial proves nothing |
| "Different words so rule doesn't apply" | Spirit over letter |

## "dishonesty, not efficiency"——道德框架的动机

最值得注意的设计选择可能不是技术性的——是道德框架。

"Claiming work is complete without verification is dishonesty, not efficiency." 这句话把最常见的 agent 合理化（"这样更高效"）重新定义为道德问题。

Superpowers 不要求 agent 更 disciplined——它要求 agent 更 honest。这是一个更强的激励：没人想被叫骗子。效率可以辩论，诚实不能。

这也和 human-partner 框架对齐：verification skill 的文档里有一条注："your human partner said 'I don't believe you' - trust broken." 跳过验证不是"省了几秒"——是冒着损害合作信任的风险。
