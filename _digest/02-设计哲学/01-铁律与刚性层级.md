# 01 — 铁律与刚性层级

## 这个问题为什么重要

Superpowers 有 14 个 skill。有的写 "NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST"（全部大写，无条件），有的写 "Adapt principles to context"（灵活，可调整）。为什么有些规则是铁律，有些只是建议？规则升级到铁律的标准是什么？

---

## Skill 分类：刚性 vs 柔性

`using-superpowers/SKILL.md` 定义了二分法：

```
Rigid (TDD, debugging): Follow exactly. Don't adapt away discipline.
Flexible (patterns): Adapt principles to context.

The skill itself tells you which.
```

| 刚性（Iron Law） | 柔性（Recommendation） |
|-----------------|---------------------|
| TDD | brainstorming |
| systematic-debugging | writing-plans |
| verification-before-completion | executing-plans |
| receiving-code-review | finishing-a-development-branch |
| writing-skills | using-git-worktrees |
| | SDD |
| | requesting-code-review |
| | dispatching-parallel-agents |

## 五条铁律

| Skill | 铁律 | 违反的后果 |
|-------|------|---------|
| TDD | NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST | 生产代码未测试、不可验证 |
| Systematic Debugging | NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST | 修错地方、引入新 bug、修复不可持续 |
| Verification | NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE | 声称完成但实际未完成、信任破裂 |
| Writing Skills | NO SKILL WITHOUT A FAILING TEST FIRST | 发布的 skill 有未发现的漏洞 |
| TDD Anti-patterns | 三条子律：NEVER test mock behavior, NEVER add test-only methods to production, NEVER mock without understanding dependencies | 测试测 mock 不是测真实行为 |

---

## 铁律的共享结构

每条铁律用完全相同的结构：

```
[标题：全部大写，无条件 imperative]

If you [条件不满足]:
[具体后果：删代码/回 Phase 1/delete and start over]

[禁止的 workaround 1]
[禁止的 workaround 2]
[禁止的 workaround 3]

No exceptions.
```

这不是格式巧合——是 testing-skills-with-subagents.md 记录的 pattern。Agent 在模糊的规则下会找例外；全部大写 + 绝对语言 + 显式否定让"这是例外吗"的认知搜索直接被消除。

---

## 什么让一条规则升级到铁律？

三个条件同时满足：

### 1. 短期成本不对称

正确的行为（写测试、调查根因、验证）在短期比捷径（跳测试、猜 fix、声称完成）更贵。

写一个 test：3 分钟。直接写代码：1 分钟。大脑自然选快的。

### 2. agent 能构建听起来合理的借口

"太简单不需要测试"——听起来像工程判断。
"我先修这个问题，之后再调查"——听起来像 pragmatism。
"应该没问题了"——听起来像 confidence。

关键：**这些借口在 agent 听起来不是借口——它们听起来是合理的工程判断。** 铁律的作用是切断这个自我欺骗的链条。

### 3. 违规是自我隐藏的

测试立刻通过不证明代码是对的（可能测试没覆盖）。一个没调查根因的 fix 可能碰巧工作一次。一个未验证的 claim 可能在下一轮被发现是错的。

**违规的后果不会立刻被感知。** Agent 在违规的当下看不到 harm——所以它感受不到"做错了"的反馈。铁律是这种"不可见 harm"的外部约束。

## 两条升级机制

### 机制 1: 3+ 失败 fix → 质疑架构

Systematic-debugging 的铁律有一个独特的升级阈值：

```
如果你尝试了 3+ 个 fix 都失败了：

STOP and question fundamentals.

- 这个 pattern 在根本上有问题吗？
- 我们还在坚持它只是因为惯性吗？
- 这不是一个失败假设——这是错误的架构。
```

不是"再试一次"——是"质疑根本设计"。这个升级防止 agent 在 local fix 的循环中耗尽时间。

### 机制 2: DONE_WITH_CONCERNS → 上上报

SDD skill 区分两种 implementer 疑虑：
- **正确性或范围的疑虑**：review 前必须先解决
- **观察性备注**（"这个文件有点大"）：记录，继续

这让 agent 不能把"文件有点大"合理化到搁置任务，也不能把"好像不太对"丢到提醒里假装解决了。

## 说服心理学基础

`persuasion-principles.md:137`:

> "Bright-line rules reduce rationalization: 'YOU MUST' removes decision fatigue. Absolute language eliminates 'is this an exception?' questions."

基于 Meyke et al. (2025)：authority 框架让 LLM 合规率从 33% → 72%（p < .001）。

刚性 skill 也在多个层面部署 Commitment：
- using-superpowers 要求宣布 skill 使用
- writing-skills 要求 checklist 转 TodoWrite
- TDD 要求先看 test 失败

这些都是 Commitment 的技术应用——agent 公开承诺一个行动之后，在心理上更难合理化背离。

## 铁律 vs 推荐：一眼区别

| | 铁律 | 推荐 |
|---|------|------|
| 语言 | 全部大写 "NO...WITHOUT...FIRST" | "should""prefer""consider" |
| 例外 | 明确禁止（"No exceptions"） | 允许根据上下文调整 |
| 违规信号 | Red Flags 表（"X = STOP"） | 无具体违规信号 |
| 借口反驳 | 借口-反驳表 | 无 |
| 门函数 | 强制性步骤序列 | 建议性流程 |
| 测试 | 需要对抗性压力测试 | 不需要 |

---

## 为什么不是所有规则都是铁律？

brainstorming 不需要铁律——agent 自然地会先设计再写代码（省事，不需要强制）。writing-plans 不需要铁律——从 spec 到 plan 的转换是一个确定的机械过程。

铁律要解决的是**"做正确的事比捷径更贵"的情况**。写测试比跳测试更贵。调查根因比 guess a fix 更贵。验证比声称完成更贵。当捷径比正确路径更便宜时，才需要铁律。
