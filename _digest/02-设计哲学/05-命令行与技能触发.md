# 05 — 命令行与技能触发：为什么没有 CLI，以及这带来的问题

## 直接回答：Superpowers 有没有命令行？

**没有。** 没有 `superpowers` CLI 二进制，没有 npm `bin` 入口，没有 slash command。

曾经有过——`/brainstorm`、`/execute-plan`、`/write-plan` 三个 slash command，但在 v5.1.0（2026-04-30）被删除了。RELEASE-NOTES 的说法是：

> "They were deprecated stubs that did nothing but tell the user to invoke the corresponding skill."

这些 slash command 从来不是真正的 CLI——它们只是重定向，告诉用户"请用 Skill 工具调用 superpowers:brainstorming"。v4.0.2 甚至加了 `disable-model-invocation: true` 防止模型自己调用它们（因为它们只是重定向，模型调了也是浪费一步）。

---

## 现在有什么"类命令行"的东西？

有一些脚本，但全是开发者工具或 skill 内部工具，不是用户面向的 CLI：

| 脚本 | 类型 | 谁用它 |
|------|------|--------|
| `scripts/bump-version.sh` | 版本管理 | 维护者 |
| `scripts/sync-to-codex-plugin.sh` | CI/CD | 维护者 |
| `hooks/session-start` | Bootstrap 注入 | 自动触发 |
| `hooks/run-hook.cmd` | 跨平台 wrapper | 自动触发 |
| `skills/brainstorming/scripts/start-server.sh` | WebSocket 服务器 | brainstorming skill 内部 |
| `skills/systematic-debugging/find-polluter.sh` | 二分查找工具 | systematic-debugging skill 内部 |
| `skills/writing-skills/render-graphs.js` | 图表渲染 | writing-skills skill 内部 |

没有一个是用户会直接敲的命令。用户和 Superpowers 的交互完全通过模型——用户说人话，模型判断要不要调 skill。

---

## 技能触发：完全依赖 prompt，没有运行时强制执行

Superpowers 的技能触发链路是：

```
用户输入 → 模型看到 using-superpowers bootstrap（已注入上下文）
         → 模型判断"是否有 1% 的可能某个 skill 适用"
         → 如果是 → 调用 Skill 工具 → skill 内容加载 → 执行
         → 如果否 → 直接回复
```

**每一步都在模型"脑子里"。没有任何 hook、validator、PreToolUse 拦截器来检查模型是否应该触发但没触发某个 skill。**

using-superpowers 的防御机制有三层：

### Layer 1: 1% Rule
```
If you think there is even a 1% chance a skill might apply,
you ABSOLUTELY MUST invoke the skill.
IF A SKILL APPLIES TO YOUR TASK, YOU DO NOT HAVE A CHOICE.
```

### Layer 2: 12 条 Red Flags 表
每条都是"模型会产生的合理化 → 预先写好的反驳"：

| Thought | Reality |
|---------|---------|
| "This is just a simple question" | Questions are tasks. Check for skills. |
| "I know what that means" | Knowing the concept ≠ using the skill. Invoke it. |
| "Let me explore the codebase first" | Skills tell you HOW to explore. Check first. |
| "The skill is overkill" | Simple things become complex. Use it. |

### Layer 3: 承诺机制
Flowchart 要求模型在遵循 skill 之前先宣布 "Using [skill] to [purpose]"——创造公开承诺。

**这三层全是 prompt。** 没有代码在执行。模型可以选择不遵守（有时不是故意的——上下文太长，它真的忘了）。

## 5 个已被文档记录在案的触发失败模式

### Failure Mode 1: CSO 描述陷阱（v4.0.0 发现）

Skill 的 YAML `description` 如果包含工作流摘要，模型会跟着摘要走而**不读 skill 正文**。SDD 的真实案例：description 写了"code review between tasks"（单数），模型做了一次 review。Skill 正文的 flowchart 明确要求**两阶段** review（spec compliance 然后 code quality），但模型没读到——description 已经告诉它"够用了"。

修复：description 只能写触发条件（"Use when X"），不能写任何工作流摘要。这是 CSO（Claude Search Optimization）的核心原则。

### Failure Mode 2: "I know what that means"（v4.0.3 发现）

用户说 "subagent-driven-development, please"——模型觉得自己知道 SDD 是什么，直接开始干活，**不调用 Skill 工具**。这意味着它用的是自己训练数据里的 SDD 知识，而不是 skill 文件里的最新版本。

修复：在 Red Flags 表里加了一条 "I know what that means" → "Knowing the concept ≠ using the skill. Invoke it." 同时把 using-superpowers 的措辞从 "Check for skills" 改为 "Invoke relevant or requested skills BEFORE any response or action"。

### Failure Mode 3: Brainstorming 完全跳过（v4.3.0）

模型跳过设计阶段，直接跳到实现 skill。或者把整个 brainstorming 过程压缩成一段文字输出。

修复：加了 `<HARD-GATE>` 标签、强制 checklist、Graphviz 流程图、EnterPlanMode 拦截（防止模型进入原生 plan mode 而不经过 brainstorming）。

### Failure Mode 4: Bootstrap 竞态条件（v4.3.0）

`hooks.json` 里 SessionStart hook 的 `async: true` 导致 hook 可能在第一轮对话之前没执行完。using-superpowers 的指令（包括 1% rule）没进上下文，模型完全不知道有 skill 这回事。

修复：改成 `async: false`，session 初始化阻塞到 hook 完成。

### Failure Mode 5: Subagent 也跳过 skill（v4.5.0）

这是故意的——加了 `<SUBAGENT-STOP>` 让 subagent 跳过 using-superpowers。但 user feedback plan（`docs/plans/2025-11-28-skills-improvements-from-user-feedback.md` 第 178 行）承认了由此产生的 gap：

> "No enforcement that subagents read relevant skills. No prompt includes skill reading."

Subagent 不读 using-superpowers，不知道有 skill，自然也不会调用 skill。

## 为什么 Superpowers 没有运行时强制执行？

这是一个**设计选择**，不是疏忽。

Superpowers 的设计哲学是：**模型的自愿合规是值得优化的机制，而不是需要替换的机制。** writing-skills 明确说：

> "Mechanical constraints (if it's enforceable with regex/validation, automate it — save documentation for judgment calls)"

翻译：能用机械约束的就自动化（lint、regex），不能的（设计流程、调试方法论）就靠文档——这些是"判断调用"，不是"机械约束"。

但 skill 触发落在一个灰色地带：**Skill 文件的加载可以是机械的**（调用 Skill 工具就是一个 tool call），**但"是否应该触发"被当作判断调用处理**。

另外，还有一个实际约束：Superpowers 支持的 6 个平台有不同的 hook 能力。Claude Code 的 hook 系统最成熟（有 SessionStart、PreToolUse 等），但 Codex、Gemini CLI 等平台没有等效的 hook。做一个只在一个平台上工作的运行时强制执行，不如做一个在所有平台上都能用的 prompt 层方案。

## 用户指出的真正问题

用户的问题可以重新表述为：

> 当模型的上下文变得很长很乱时，它可能会忘记触发 skill。Skill 都很大，模型糊涂了就不记得要调用了。如果有 CLI，轻量的事情放在 CLI 里，重的放在 skill 里——这会让整个系统更可靠。

这个诊断是对的。现有的 5 个 failure mode 里有 3 个（CSO、"I know what that means"、Brainstorming 跳过）本质上都是**模型在决定"不需要调 skill"**。它不是故意违反规则——它真的觉得不需要。

prompt 层的防御一直在迭代——从 v3.2.2 的 1% rule 到 v4.3.0 的 HARD-GATE，每个版本的措辞都在加强。但这是一场没有终点的军备竞赛：

1. 写更强的措辞 → 模型暂时遵守
2. 模型在新的压力场景下找到新的合理化 → 绕过
3. 再加强措辞 → ...

CLI 可以做的是**绕过模型的主观判断**。如果用户敲了 `superpowers brainstorm`，模型不需要判断"是否有 1% 的可能适用"——用户已经告诉它要用了。CLI 把"判断调用"变成了"机械调用"。

## CLI vs Prompt：各自擅长的场景

| 维度 | Prompt 层（现状） | CLI（如果存在） |
|------|-----------------|---------------|
| **触发方式** | 模型自主判断 | 用户显式指令 |
| **适用场景** | 模型能正确识别上下文的简单情况 | 长 session、上下文混乱、模型反复不触发 |
| **可靠性** | 依赖模型当时的注意力状态 | 确定性——调了就加载 |
| **成本** | 零——不需要额外设施 | 需要为每个平台开发、测试、维护 |
| **用户体验** | 自然语言，无缝 | 需要记住命令名 |
| **跨平台** | 一个 prompt 在所有平台工作 | 每个平台的命令机制不同 |

最优方案可能不是二选一，而是**CLI 作为 prompt 层的补充**：

- Prompt 层处理日常的自动触发（模型自主判断，大部分时候是对的）
- CLI 作为逃生舱——当模型没触发时，用户不需要说服它，直接敲命令
- CLI 也可以处理轻量操作（如 `superpowers skill list` 列出可用 skill），这些不需要加载完整的 skill 文件

## Slash Command 为什么失败了——以及真正的 CLI 应该怎么不一样

被删除的 `/brainstorm` 等 slash command 失败的原因是**它们是假命令**——它们不执行任何逻辑，只是输出一条消息告诉用户"请调 skill"。这不是 CLI，是帮助文档伪装成命令。

真正的 CLI 应该：
- **直接触发 Skill 工具**——不经过模型判断，直接把 skill 内容注入上下文
- **提供轻量操作**——列出 skill、查看 skill 状态、检查当前 PLAN 进度，这些不需要加载完整 skill
- **是模型可调用的**——模型在意识到自己应该用某个 skill 时，可以调用 CLI 而不是依赖自己的"记得去调 Skill 工具"

技术上，在 Claude Code 里这可以实现为：一个 user-only 的 slash command，它的 handler 直接调用 Skill 工具加载指定 skill。这不是"重定向"——这是绕过模型判断的直达通道。
